## 1. What dbt is

**dbt (data build tool)** is the **T in ELT**. You write `SELECT` statements (models) plus YAML config; dbt compiles Jinja+SQL, resolves dependencies into a DAG, and materializes results in your warehouse (Snowflake, BigQuery, Databricks, Redshift, Postgres, DuckDB, Trino, etc.).

| dbt does | dbt does not |
|---|---|
| Transform data already in the warehouse | Extract/load data (use Fivetran, Airbyte, etc.) |
| Dependency management via `ref()` / `source()` | Orchestrate on its own (Core) – use Airflow, Dagster, Prefect, dbt Cloud jobs |
| Test, document, version-control SQL | Replace a BI tool |
| Generate lineage & docs | Run Python outside warehouse (Python models run in warehouse engines) |

**Flavors**
- **dbt Core**: open-source CLI (Python, Apache 2.0).
- **dbt Cloud / platform**: hosted IDE, scheduler, CI, Catalog (Explorer), Semantic Layer, Mesh.
- **dbt Fusion engine**: Rust-based engine (faster parse/compile, static SQL analysis, VS Code extension). Mostly compatible with Core project syntax; check deprecations.

**Mental model**
```
raw sources ──> staging (clean/rename/cast) ──> intermediate (join/logic) ──> marts (facts/dims, business-ready) ──> BI/ML/reverse-ETL
```

## 2. Installation & setup

```bash
# Python venv recommended
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate

pip install dbt-core dbt-snowflake      # pick adapter: dbt-bigquery, dbt-databricks, dbt-postgres, dbt-redshift, dbt-duckdb, dbt-trino ...
dbt --version

dbt init my_project                     # scaffold project + profile entry
cd my_project
dbt debug                               # verify profile, connection, dependencies
dbt deps                                # install packages
dbt build                               # run + test everything
```

Other options: `uv pip install`, Docker images (`ghcr.io/dbt-labs/dbt-<adapter>`), dbt Cloud CLI (`dbt` binary via Cloud), Fusion installer.

## 3. Project structure

```
my_project/
├── dbt_project.yml          # project config (required)
├── profiles.yml             # connections (usually in ~/.dbt/, not committed)
├── packages.yml             # package deps (or dependencies.yml)
├── selectors.yml            # named selectors
├── package-lock.yml         # pinned package versions (generated by dbt deps)
├── models/
│   ├── staging/
│   │   ├── stripe/
│   │   │   ├── _stripe__sources.yml
│   │   │   ├── _stripe__models.yml
│   │   │   ├── stg_stripe__payments.sql
│   │   │   └── stg_stripe__customers.sql
│   ├── intermediate/
│   │   └── finance/int_payments_pivoted_to_orders.sql
│   └── marts/
│       ├── finance/
│       │   ├── _finance__models.yml
│       │   ├── fct_orders.sql
│       │   └── dim_customers.sql
│       └── marketing/
├── seeds/                   # CSV reference data
├── snapshots/               # SCD2 (YAML or SQL definitions)
├── macros/                  # Jinja macros (.sql)
├── tests/                   # singular data tests (.sql)
│   └── generic/             # custom generic tests (or in macros/)
├── analyses/                # compiled-only SQL (not materialized)
├── docs/                    # doc blocks (.md)
├── target/                  # build artifacts (gitignored)
├── dbt_packages/            # installed packages (gitignored)
└── logs/                    # gitignored
```

**Naming conventions (dbt Labs style)**
| Layer | Prefix | Example | Typical materialization |
|---|---|---|---|
| Staging | `stg_<source>__<entity>` | `stg_stripe__payments` | view (or table for large) |
| Intermediate | `int_<entity>s_<verb>` | `int_orders_joined_payments` | ephemeral / view / table |
| Marts – facts | `fct_<verb/noun>` | `fct_orders` | table / incremental |
| Marts – dimensions | `dim_<noun>` | `dim_customers` | table |
| Metrics/semantic | `metrics_*` | | |

`.gitignore`: `target/`, `dbt_packages/`, `logs/`, `.user.yml`, `profiles.yml` (if local).

## 4. Core config files

### 4.1 `dbt_project.yml`
```yaml
name: 'jaffle_shop'
version: '1.0.0'
config-version: 2
profile: 'jaffle_shop'                # must match profiles.yml key

require-dbt-version: [">=1.9.0", "<2.0.0"]

model-paths: ["models"]
seed-paths: ["seeds"]
test-paths: ["tests"]
analysis-paths: ["analyses"]
macro-paths: ["macros"]
snapshot-paths: ["snapshots"]
docs-paths: ["docs"]
asset-paths: ["assets"]
clean-targets: ["target", "dbt_packages"]

vars:
  start_date: '2020-01-01'
  is_ci: false

flags:                                 # project-level behavior flags
  require_explicit_package_overrides_for_builtin_materializations: true
  send_anonymous_usage_stats: false
  # state_modified_compare_more_unrendered_values: true

on-run-start:
  - "{{ log('Starting run on ' ~ target.name, info=True) }}"
on-run-end:
  - "{{ grant_select_on_schemas(schemas, 'reporter') }}"

models:
  jaffle_shop:
    +materialized: view
    +on_schema_change: append_new_columns
    staging:
      +materialized: view
      +schema: staging
      +tags: ['staging']
    intermediate:
      +materialized: ephemeral
    marts:
      +materialized: table
      +schema: marts
      finance:
        +tags: ['finance', 'nightly']
        +contract: {enforced: true}
      marketing:
        +materialized: incremental

seeds:
  jaffle_shop:
    +schema: seeds
    +quote_columns: false
    country_codes:
      +column_types: {code: varchar(2)}

snapshots:
  jaffle_shop:
    +target_schema: snapshots

data_tests:
  +store_failures: true
  +severity: warn

sources:
  jaffle_shop:
    +freshness:
      warn_after: {count: 12, period: hour}

tests: {}                              # legacy alias for data_tests
```

**Config precedence (lowest → highest):** `dbt_project.yml` folder-level → properties `.yml` `config:` → in-file `{{ config() }}` block. More specific wins. `+` prefix disambiguates configs from folder names (recommended).

### 4.2 `profiles.yml` (`~/.dbt/profiles.yml`)
```yaml
jaffle_shop:
  target: dev                          # default target
  outputs:
    dev:
      type: snowflake
      account: "{{ env_var('SNOWFLAKE_ACCOUNT') }}"
      user: "{{ env_var('DBT_USER') }}"
      password: "{{ env_var('DBT_PASSWORD') }}"
      role: TRANSFORMER
      database: ANALYTICS_DEV
      warehouse: TRANSFORMING_XS
      schema: dbt_{{ env_var('DBT_USER') }}
      threads: 4
    prod:
      type: snowflake
      account: "{{ env_var('SNOWFLAKE_ACCOUNT') }}"
      user: SVC_DBT
      private_key_path: "{{ env_var('DBT_PRIVATE_KEY_PATH') }}"
      role: TRANSFORMER
      database: ANALYTICS
      warehouse: TRANSFORMING_M
      schema: analytics
      threads: 8
```
- Location lookup: `--profiles-dir` → `DBT_PROFILES_DIR` → current dir → `~/.dbt/`.
- Secrets: `env_var('X')` (use `DBT_ENV_SECRET_` prefix so values are scrubbed from logs).
- BigQuery: `method: oauth | service-account`, `project`, `dataset`, `location`.
- Databricks: `host`, `http_path`, `token`/OAuth, `catalog`, `schema`.
- Postgres/Redshift: `host`, `port`, `user`, `password`, `dbname`, `schema`.
- DuckDB: `path: dev.duckdb`.

### 4.3 `packages.yml` / `dependencies.yml`
```yaml
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.1.0", "<2.0.0"]
  - package: calogica/dbt_expectations
```

### 4.4 `selectors.yml`
```yaml
selectors:

    description: "Finance marts and their upstream, excluding slow models"
    default: false

        - method: tag
          value: finance
          parents: true
        - exclude:
            - method: tag
              value: slow
  - name: ci_slim
    definition:
      method: state
      value: modified
      children: true
```
Use: `dbt build --selector nightly_finance`.

## 5. Resource types

| Resource | Defined in | Materialized? | Purpose |
|---|---|---|---|
| **model** | `.sql` / `.py` | yes | transformation |
| **source** | YAML | no | declare raw tables, freshness |
| **seed** | `.csv` | yes (table) | small static data |
| **snapshot** | YAML/SQL | yes | SCD Type 2 history |
| **test (data_test)** | YAML / `.sql` | query only | assertions |
| **unit_test** | YAML | in-memory/ CTE | validate logic w/ mocked inputs |
| **macro** | `.sql` | no | reusable Jinja |
| **analysis** | `.sql` | no | compiled ad-hoc SQL |
| **exposure** | YAML | no | downstream dashboards/apps |
| **metric / semantic_model / saved_query** | YAML | no (query-time) | Semantic Layer |
| **group** | YAML | no | ownership |
| **doc block** | `.md` | no | reusable docs |

`unique_id` format: `model.jaffle_shop.fct_orders`, `source.jaffle_shop.stripe.payments`, `test.jaffle_shop.not_null_fct_orders_order_id.abc123`.

## 6. Models & materializations

### 6.1 Basic model
```sql
-- models/marts/finance/fct_orders.sql
{{ config(materialized='table', tags=['finance']) }}

with orders as (
    select * from {{ ref('stg_shop__orders') }}
),
payments as (
    select order_id, sum(amount) as total_paid
    from {{ ref('stg_stripe__payments') }}
    where status = 'success'
    group by 1
)
select
    o.order_id,
    o.customer_id,
    o.ordered_at,
    coalesce(p.total_paid, 0) as total_paid
from orders o
left join payments p using (order_id)
```
Rules: one SELECT (CTEs allowed); no trailing semicolon; filename = model name (unique per project); dbt wraps in `CREATE ... AS`.

### 6.2 Materializations
| Type | What | Build cost | Query speed | Use when |
|---|---|---|---|---|
| `view` | `CREATE VIEW` | none | slow if deep chain | staging, small/rarely queried |
| `table` | `CREATE TABLE AS` (full rebuild) | rebuild each run | fast | marts, BI-facing |
| `incremental` | insert/merge only new rows | low | fast | large event/fact tables |
| `ephemeral` | inlined as CTE | none | n/a | light reusable logic; cannot be queried/ tested directly via `ref` target |
| `materialized_view` | warehouse-managed MV | warehouse refresh | fast | near-real-time, supported adapters |
| `snapshot` | SCD2 history | incremental | – | track changes |
| `dynamic_table` (Snowflake) | declarative refresh via `target_lag` | managed | fast | streaming-ish pipelines |
| `streaming_table` (Databricks) | | | | ingestion |
| custom | user-defined macro `materialization` | | | special needs |

```sql
{{ config(materialized='materialized_view', on_configuration_change='apply') }}
{{ config(materialized='dynamic_table', snowflake_warehouse='XS', target_lag='10 minutes') }}
```

### 6.3 Common model configs
```sql
{{ config(
    materialized = 'table',
    schema = 'marts',                       -- appended to target schema by default (see generate_schema_name)
    database = 'analytics',
    alias = 'orders',                        -- relation name different from file name
    tags = ['nightly'],
    meta = {'owner': 'finance', 'pii': false},
    enabled = true,
    full_refresh = false,                    -- block --full-refresh for this model
    persist_docs = {'relation': true, 'columns': true},
    grants = {'select': ['reporter', 'analyst']},
    contract = {'enforced': true},
    pre_hook = "...", post_hook = "...",
    on_schema_change = 'fail',               -- ignore | append_new_columns | sync_all_columns | fail
    docs = {'show': true, 'node_color': '#ff0000'},
    group = 'finance',
    access = 'public'                        -- private | protected | public
) }}
```

Warehouse-specific examples:
```sql
-- BigQuery
{{ config(partition_by={'field':'order_date','data_type':'date','granularity':'day'},
          cluster_by=['customer_id'], require_partition_filter=true) }}
-- Snowflake
{{ config(cluster_by=['order_date'], transient=true, copy_grants=true, snowflake_warehouse='L') }}
-- Databricks
{{ config(file_format='delta', partition_by=['order_date'], liquid_clustered_by=['customer_id']) }}
-- Redshift
{{ config(dist='customer_id', sort=['order_date'], sort_type='compound') }}
```

### 6.4 Python models
```python
# models/ml/customer_features.py
def model(dbt, session):
    dbt.config(materialized="table", packages=["pandas", "scikit-learn"])
    orders = dbt.ref("fct_orders")          # DataFrame (Snowpark / PySpark / BigQuery DF)
    src = dbt.source("stripe", "payments")
    df = orders.to_pandas() if hasattr(orders, "to_pandas") else orders
    df["is_big"] = df["total_paid"] > 100
    return df
```
Supported on Snowflake (Snowpark), Databricks (PySpark), BigQuery (Dataproc/BigFrames). Use for ML/feature engineering, not for what SQL does well.

### 6.5 Ephemeral caveat
Ephemeral models are interpolated as CTEs, cannot have tests that select from them standalone in some contexts, and long chains hurt readability of compiled SQL. Prefer `view`/`table` for debuggability.

### 6.6 Custom schema / database naming (`generate_schema_name`)
Default: `<target.schema>_<custom_schema>` (e.g. `dbt_alice_staging`). Override for prod:
```sql
-- macros/generate_schema_name.sql
{% macro generate_schema_name(custom_schema_name, node) -%}
    {%- set default_schema = target.schema -%}
    {%- if target.name == 'prod' and custom_schema_name is not none -%}
        {{ custom_schema_name | trim }}
    {%- elif custom_schema_name is none -%}
        {{ default_schema }}
    {%- else -%}
        {{ default_schema }}_{{ custom_schema_name | trim }}
    {%- endif -%}
{%- endmacro %}
```
Sibling overrides: `generate_database_name`, `generate_alias_name`.

## 7. Incremental models in depth

```sql
{{ config(
    materialized='incremental',
    unique_key='event_id',
    incremental_strategy='merge',
    on_schema_change='append_new_columns',
    partition_by={'field':'event_date','data_type':'date'}   -- adapter-specific
) }}

select event_id, user_id, event_ts, event_type, payload
from {{ ref('stg_app__events') }}

{% if is_incremental() %}
  -- only rows newer than what's already in this table
  where event_ts > (select coalesce(max(event_ts), '1900-01-01') from {{ this }})
{% endif %}
```

### Key concepts
- `is_incremental()` true when: model exists, is materialized incremental, and run is **not** `--full-refresh`.
- `{{ this }}` = existing target relation.
- `unique_key` (string or list) → upsert; without it → append only.
- Rebuild: `dbt run --full-refresh -s my_model`.

### Strategies
| Strategy | Mechanism | Adapters | Notes |
|---|---|---|---|
| `append` | insert only | all | duplicates possible |
| `merge` | MERGE on unique_key | Snowflake, BigQuery, Databricks | supports `merge_update_columns`, `merge_exclude_columns` |
| `delete+insert` | delete matching keys, insert | Snowflake, Postgres, Redshift | fine for batches |
| `insert_overwrite` | overwrite partitions | BigQuery, Spark/Databricks | needs partition config; static/dynamic partitions |
| `microbatch` | time-sliced independent batches | dbt Core ≥1.9 | `event_time`, `batch_size`, `lookback`, `begin`; no `is_incremental()` needed |
| custom | user macro `get_incremental_<name>_sql` | | |

### Microbatch (1.9+)
```sql
{{ config(
    materialized='incremental',
    incremental_strategy='microbatch',
    event_time='event_ts',
    batch_size='day',            -- hour | day | month | year
    lookback=2,                  -- reprocess last N batches
    begin='2024-01-01',
    concurrent_batches=true
) }}
select * from {{ ref('stg_app__events') }}     -- upstream must declare event_time too
```
Upstream model config: `event_time: event_ts`. Backfill: `dbt run --event-time-start "2024-01-01" --event-time-end "2024-02-01"`. Retry failed batches: `dbt retry`.

### Pitfalls & tips
- Late-arriving data: use lookback window (`where event_ts >= dateadd(day,-3,(select max(event_ts) from {{ this }}))`).
- Deleted source rows are not propagated; use periodic full refresh or soft-delete flags.
- Schema drift: set `on_schema_change`.
- Test the incremental logic with unit tests (`overrides: macros: is_incremental: true`).
- Make the filter sargable (partition/cluster-aligned) to prune scans.

## 8. Sources, seeds, snapshots

### 8.1 Sources
```yaml
# models/staging/stripe/_stripe__sources.yml
version: 2
sources:
  - name: stripe
    description: "Stripe payments loaded by Fivetran"
    database: raw
    schema: stripe
    config:
      loaded_at_field: _fivetran_synced
      freshness:
        warn_after: {count: 6, period: hour}
        error_after: {count: 24, period: hour}
    tables:
      - name: payments
        identifier: payment_raw        # actual table name
        description: "One row per payment"
        columns:
          - name: id
            data_tests: [unique, not_null]
      - name: customers
        config:
          freshness: null              # disable for this table
```
Use: `select * from {{ source('stripe', 'payments') }}`.
Check: `dbt source freshness` (outputs `target/sources.json`). Select: `dbt build --select source_status:fresher+` (with state).

### 8.2 Seeds
`seeds/country_codes.csv` → `dbt seed` → `{{ ref('country_codes') }}`.
```yaml
seeds:
  - name: country_codes
    config:
      column_types: {code: varchar(2)}
      delimiter: ","
      quote_columns: false
```
Use for small, rarely-changing lookups (<~1MB). Not for loading real data.

### 8.3 Snapshots (SCD Type 2)
**YAML (1.9+, recommended)**
```yaml
# snapshots/orders_snapshot.yml
snapshots:
  - name: orders_snapshot
    relation: source('shop', 'orders')       # or ref('...')
    config:
      schema: snapshots
      unique_key: order_id
      strategy: timestamp                    # timestamp | check
      updated_at: updated_at
      # strategy: check ; check_cols: [status, amount]  (or 'all')
      hard_deletes: invalidate               # ignore | invalidate | new_record
      dbt_valid_to_current: "to_date('9999-12-31')"
      snapshot_meta_column_names:
        dbt_valid_from: valid_from
        dbt_valid_to: valid_to
```
**Legacy SQL (still supported)**
```sql
{% snapshot orders_snapshot %}
{{ config(target_schema='snapshots', unique_key='order_id', strategy='timestamp', updated_at='updated_at') }}
select * from {{ source('shop','orders') }}
{% endsnapshot %}
```
Generated columns: `dbt_scd_id`, `dbt_updated_at`, `dbt_valid_from`, `dbt_valid_to`.
Run: `dbt snapshot`. Query current rows: `where dbt_valid_to is null`.
Tips: snapshot **sources** (raw), keep logic minimal, run frequently, protect in prod (cannot be rebuilt from history).

## 9. Testing

### 9.1 Generic (data) tests — built-in
```yaml
models:
  - name: fct_orders
    description: "One row per order"
    data_tests:                              # model-level tests
      - dbt_utils.unique_combination_of_columns:
          combination_of_columns: [order_id, line_number]
    columns:
      - name: order_id
        data_tests:
          - unique
          - not_null
      - name: status
        data_tests:
          - accepted_values:
              values: ['placed','shipped','returned','completed']
              config: {severity: warn}
      - name: customer_id
        data_tests:
          - relationships:
              to: ref('dim_customers')
              field: customer_id
              config:
                where: "ordered_at > current_date - 30"
                store_failures: true
                error_if: ">100"
                warn_if: ">0"
                limit: 50
```
| Built-in | Asserts |
|---|---|
| `unique` | no duplicates |
| `not_null` | no nulls |
| `accepted_values` | values in list (`quote: false` for numerics) |
| `relationships` | FK exists in parent |

Test configs: `severity` (warn/error), `error_if`, `warn_if`, `where`, `limit`, `fail_calc` (default `count(*)`), `store_failures`, `store_failures_as` (table/view), `tags`, `name`, `meta`.
> Key renamed `tests:` → `data_tests:` in 1.8 (both accepted). A test passes when its query returns **zero rows** (or `fail_calc` within thresholds).

### 9.2 Singular tests
```sql
-- tests/assert_no_negative_revenue.sql
select order_id, total_paid
from {{ ref('fct_orders') }}
where total_paid < 0
```

### 9.3 Custom generic tests
```sql
-- tests/generic/test_is_positive.sql   (or macros/)
{% test is_positive(model, column_name) %}
select * from {{ model }} where {{ column_name }} <= 0
{% endtest %}
```
Use: `data_tests: [is_positive]`. With args: `{% test within_range(model, column_name, min_val, max_val) %}`.

### 9.4 Unit tests (1.8+)
Validate SQL **logic** with static mock inputs, before materializing (dev/CI only).
```yaml
unit_tests:
  - name: test_order_status_mapping
    model: fct_orders
    given:
      - input: ref('stg_shop__orders')
        rows:
          - {order_id: 1, status_code: 'S', amount: 10}
          - {order_id: 2, status_code: 'R', amount: 20}
      - input: source('stripe','payments')
        format: csv
        rows: |
          order_id,amount,status
          1,10,success
    expect:
      rows:
        - {order_id: 1, status: shipped, total_paid: 10}
        - {order_id: 2, status: returned, total_paid: 0}
    overrides:
      macros:
        is_incremental: false
      vars: {start_date: '2024-01-01'}
      env_vars: {ENV: ci}
```
Formats: `dict` (default), `csv`, `sql`, or `fixture:` files in `tests/fixtures/`. Run: `dbt test --select "test_type:unit"`; exclude in prod: `--exclude-resource-type unit_test`.
Use for: complex CASE logic, regex, window functions, date math, incremental branches. Not for data quality of real data.

### 9.5 Contracts & constraints (shape tests at build time)
```yaml
models:
  - name: dim_customers
    config: {contract: {enforced: true}}
    constraints:
      - type: primary_key
        columns: [customer_id]
    columns:
      - name: customer_id
        data_type: int
        constraints:
          - type: not_null
          - type: primary_key
      - name: email
        data_type: varchar
```
Constraint types: `not_null`, `unique`, `primary_key`, `foreign_key`, `check`, `custom`. Enforcement varies by warehouse (Snowflake/Redshift: PK/FK informational; Postgres enforces; BigQuery informational).

### 9.6 Testing strategy pyramid
1. **Sources**: freshness + unique/not_null on keys.
2. **Staging**: PK unique/not_null, accepted_values on enums.
3. **Marts**: grain tests, relationships, business rules, row-count / reconciliation vs source.
4. **Unit tests** for complex logic; **contracts** at public interfaces.
5. Package tests: `dbt_utils` (`equal_rowcount`, `recency`, `expression_is_true`, `not_accepted_values`, `at_least_one`, `not_constant`, `unique_combination_of_columns`, `accepted_range`, `fewer_rows_than`, `equality`), `dbt_expectations` (distribution, regex, type checks), `elementary` (anomaly detection).

Run: `dbt test -s fct_orders`, `dbt test --select "source:*"`, `dbt test --store-failures`, `dbt build` (run+test per node in DAG order, skip downstream on failure).

```yaml
semantic_models:

        expr: total_paid

    label: Revenue

    type: ratio

  - name: revenue_growth_mom
```

## 21. Data modeling patterns with dbt

### 21.1 Layered architecture (recommended)
1. **Sources** – declare, never transform.
2. **Staging** – 1:1 with source tables; rename, cast, light cleaning, no joins, no aggregations. Only layer allowed to `source()`.
3. **Intermediate** – joins, pivots, business logic, reusable building blocks.
4. **Marts** – wide, business-defined entities (facts/dims) at known grain.
5. **Semantic/metrics** – governed KPIs.

### 21.2 Kimball dimensional modeling
- **Facts**: transaction (`fct_orders`), periodic snapshot (`fct_account_balance_daily`), accumulating snapshot (`fct_order_lifecycle`), factless.
- **Dimensions**: conformed (`dim_date`, `dim_customer`), junk, degenerate (kept in fact), role-playing (alias `dim_date` as `order_date`, `ship_date`), outrigger.
- **Surrogate keys**: `dbt_utils.generate_surrogate_key([...])`.
- **SCD**: Type 1 (overwrite via table/merge), Type 2 (snapshots / `valid_from`/`valid_to` joins), Type 3 (previous-value columns), Type 6 hybrid.
- **Point-in-time join to SCD2**:
```sql
select f.*, d.segment
from {{ ref('fct_orders') }} f
left join {{ ref('customers_snapshot') }} d
  on f.customer_id = d.id
 and f.ordered_at >= d.dbt_valid_from
 and f.ordered_at <  coalesce(d.dbt_valid_to, '9999-12-31')
```
- **Grain first**: state grain in description; test with `unique_combination_of_columns`.

### 21.3 Other approaches
| Pattern | dbt implementation |
|---|---|
| **One Big Table (OBT)** | wide mart denormalizing fact+dims for BI performance |
| **Data Vault 2.0** | raw vault (hubs, links, satellites via `automate-dv`) → business vault → marts as information layer |
| **Inmon / 3NF core** | normalized core models in intermediate, marts as star schemas |
| **Medallion (bronze/silver/gold)** | bronze = sources/raw, silver = staging+intermediate, gold = marts |
| **Activity schema / event stream** | single incremental event table + derived entity models |
| **Mesh / domain-oriented** | per-domain projects, public contracts |

### 21.4 Common SQL patterns
```sql
-- Dedup latest record per key
select * from {{ ref('stg_events') }}
qualify row_number() over (partition by id order by updated_at desc) = 1   -- Snowflake/BigQuery/Databricks
-- or: {{ dbt_utils.deduplicate(ref('stg_events'), partition_by='id', order_by='updated_at desc') }}

-- Surrogate key
{{ dbt_utils.generate_surrogate_key(['customer_id','ordered_at']) }}

-- Sessionization
with e as (select *, lag(event_ts) over (partition by user_id order by event_ts) as prev_ts from {{ ref('stg_events') }}),
f as (select *, case when prev_ts is null or datediff('minute', prev_ts, event_ts) > 30 then 1 else 0 end as new_session from e)
select *, sum(new_session) over (partition by user_id order by event_ts) as session_seq from f

-- Gaps and islands, running totals, cohort retention: use window functions in intermediate models

-- Dynamic pivot: see §10.8
-- Union similar tables: {{ dbt_utils.union_relations(relations=[ref('a'), ref('b')]) }}
-- Select all except: select {{ dbt_utils.star(ref('stg_x'), except=['_loaded_at']) }}
```

### 21.5 CTE style
Import CTEs at top (`with orders as (select * from {{ ref(...) }})`), logical CTEs in middle, `final` CTE, then `select * from final`. One logical step per CTE, descriptive names, no subqueries in `from`.

## 22. Best practices

### Project & code
1. **Follow layers & naming** (§3). Staging is the only place using `source()`; marts never read sources.
2. **DRY with macros** but prioritize readability; avoid over-engineering Jinja.
3. **Use `ref()`/`source()` always**; never hardcode `db.schema.table`.
4. **Materialization ladder**: view → table → incremental; only escalate when needed.
5. **Explicit columns in marts**; `select *` ok in staging-imports/CTE imports only.
6. **Lowercase, snake_case**, trailing-comma-free; use SQLFluff + `.sqlfluff` config with `templater = dbt`.
7. **One model = one purpose**, avoid >300 lines; split to intermediates.
8. **Keep `dbt_project.yml` config folder-level**; per-model `config()` only for exceptions.
9. **Do not use `limit` in prod**; use `--empty`/`--sample`, or `target.name == 'dev'` filters via macros.
10. **Prefer `data_tests:` key and YAML for snapshots** (current syntax).
11. **Pin package versions** (ranges `[">=1.1.0","<2.0.0"]`), commit `package-lock.yml`.
12. **Use `dbt_project_evaluator`** to enforce DAG hygiene (no skipping layers, no fan-out from staging, documented models, tested PKs).

### Testing & quality
13. Every model has a **tested primary key** (`unique`+`not_null`).
14. Test **sources** and enable **freshness**.
15. Use **severity/thresholds** (`warn_if`/`error_if`) to avoid alert fatigue; keep errors for what blocks consumers.
16. **Unit-test complex logic**, not simple selects.
17. **Contracts + `access: public`** for interfaces consumed by other teams/tools.
18. Store failures (`--store-failures`) for triage dashboards.
19. Reconcile aggregates against source totals in singular tests.

### Performance & cost
20. Incremental for large facts; partition/cluster aligned with filters.
21. Avoid long view chains (>3–4) in BI-facing paths; materialize at marts.
22. Select only needed columns; push filters upstream early.
23. Right-size warehouses per environment/job; use `snowflake_warehouse` config for heavy models.
24. Use `--select` with state in CI; `dbt clone` for fast dev environments.
25. Tune `threads` to warehouse concurrency (typically 4–16).

### Workflow & team
26. Git flow: feature branch → PR → CI (lint, slim build, unit tests) → merge → prod job.
27. Separate **dev/ci/prod** targets & schemas; dev schema per user; ci schema per PR (drop afterwards).
28. Document **why**, not just what; keep descriptions for all marts & columns used downstream; `persist_docs` for warehouse comments.
29. Use **tags/groups/meta** for ownership, SLA, PII.
30. **Principle of least privilege**: dbt role writes only to its schemas; BI role read-only via `grants`.
31. **Don't snapshot transformed data**; snapshot sources.
32. **Idempotency**: models must be re-runnable; incrementals must tolerate late/duplicate data.
33. Treat **breaking changes** with model versions + deprecation dates.
34. Handle **PII**: hash/mask in staging, tag with `meta: {pii: true}`, use masking policies via post-hooks/grants.
35. Prefer **ELT-native** warehouse functions over Python models unless ML/complex.

### Anti-patterns
| Anti-pattern | Fix |
|---|---|
| Mega-model with 20 joins | split into intermediates |
| Business logic in staging | move to intermediate/marts |
| Joins in staging | only rename/cast; join later |
| Mart referencing other mart in a cycle-ish web | consolidate shared logic in intermediate |
| `select *` into marts | explicit list/contracts |
| Hardcoded dates/IDs | vars/seeds |
| Everything as table | views for staging |
| No tests on keys | add unique/not_null |
| Full-refresh nightly of huge facts | incremental/microbatch |
| Secrets in profiles | `env_var` / secret manager |
| Using seeds for large data | load via EL tool |
| Ephemeral everywhere | views/tables for debuggability |
| Ignoring warnings | `--warn-error-options` in CI |

| **Regulatory / finance reporting** | Reproducible, version-controlled, documented lineage | docs, snapshots, contracts, CI |
| **Multi-tenant / multi-region** | Parameterized models | vars, `generate_schema_name`, dispatch |
| **Data Vault implementation** | Hubs/links/sats via packages | `automate-dv`, incremental |
| **Dev sandboxes** | Zero-copy cloned environments | `dbt clone`, defer |
| **Cost governance** | Slim CI, incremental, selective builds | state selectors, `--empty`, `--sample` |
| **Lineage & impact analysis** | Know what breaks before merging | DAG, `state:modified+`, exposures |
| **Ad-hoc admin automation** | DDL/grants via macros | `run-operation`, hooks |

### Use case walkthrough: slim nightly + CI
- **Nightly job**: `dbt source freshness` → `dbt build --exclude tag:weekly` → `dbt docs generate` → publish artifacts.
- **PR CI**: `dbt build -s state:modified+ --defer --state prod-artifacts` into `ci_pr_<n>` schema; sqlfluff; drop schema after.
- **Weekly**: `dbt build -s tag:weekly --full-refresh -s config.materialized:incremental` for reconciliation.
- **Failure recovery**: `dbt retry` or `dbt build -s result:error+ --state target`.

### Use case walkthrough: legacy migration with parity checks
1. Stage the legacy source tables (`source()`).
2. Rebuild logic as staging→intermediate→marts.
3. Compare with `audit_helper.compare_relations` / `compare_column_values`; log diffs in a model.
4. Cut over BI by swapping exposures; deprecate legacy with `deprecation_date`.

## 24. Performance & cost tuning

| Lever | How |
|---|---|
| Parse time | `dbt parse`; partial parsing; reduce giant YAMLs; Fusion engine for big projects |
| Run time | `--threads`, critical-path optimization (check `run_results.json` timing; `dbt-artifacts`/Catalog) |
| Query shape | filter early, avoid cross joins/`select distinct` abuse, use `qualify`, approximate aggs where acceptable |
| Storage layout | partition/cluster/sort/dist keys per warehouse |
| Incremental | microbatch, insert_overwrite for partitioned data, lookback windows |
| Dev speed | `--empty`, `--sample`, `limit` in dev via macro, `--defer`, `dbt clone`, select subsets (`-s +model`) |
| Testing cost | `where` clauses to limit scans, `limit`, schedule heavy tests separately, `--indirect-selection cautious` |
| Warehouse sizing | per-model warehouse (Snowflake), separate heavy jobs |
| Views vs tables | materialize hot, expensive shared models |
| Artifacts | analyze `run_results.json` for slowest models: `jq '.results|sort_by(-.execution_time)|.[:10]|.[]|{id:.unique_id,t:.execution_time}' target/run_results.json` |

## 25. Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| `Could not find profile named X` | `profile:` in `dbt_project.yml` ≠ profiles.yml key; check `--profiles-dir` |
| `Compilation Error: Model X depends on a node named Y which was not found` | typo / disabled / wrong package; `dbt ls -s Y` |
| `Found a cycle` | circular `ref()`; refactor shared logic upstream |
| `Database Error ... does not exist` | upstream not built; run `-s +model`, or use `--defer --state` |
| Incremental model missing new column | set `on_schema_change` or `--full-refresh` |
| Duplicate rows in incremental | missing/incorrect `unique_key`; strategy `append` |
| Test passes locally, fails in CI | data volume/env differences; check target/`where` filters |
| `dbt_utils` macro not found | `dbt deps` not run / version mismatch / dispatch order |
| Slow `dbt run` start | large project parse; use partial parsing; `--no-partial-parse` only if corrupted |
| Stale docs | rerun `dbt docs generate` |
| `run_query` returns nothing at parse | guard with `{% if execute %}` |
| Wrong schema names in prod | override `generate_schema_name` |
| Config not applied | missing `+` prefix or wrong path in `dbt_project.yml`; inspect with `dbt ls --output json --output-keys config` |
| Unit test fails on incremental model | set `overrides: macros: is_incremental: true` and mock `this` |
| Snapshot duplicates | non-unique `unique_key`; fix source / dedup beforehand |
| Env var not found | `env_var('X','default')` or export it; secrets prefix `DBT_ENV_SECRET_` |

Debug helpers:
```bash
dbt debug --config-dir
dbt compile -s model --debug
dbt ls -s model --output json
cat target/run/<project>/models/.../model.sql      # actual executed DDL/DML
cat logs/dbt.log
```
In Jinja: `{{ log(var_or_obj, info=True) }}`, `{{ print(tojson(model)) }}`, `{% do exceptions.raise_compiler_error(...) %}`.

### 26.3 Materialization decision guide
```
Is it queried rarely or cheap?            → view
Is it BI-facing and rebuilds in <few min? → table
Is the source append-heavy/very large?    → incremental (microbatch if time-series)
Is it a tiny reusable CTE?                → ephemeral
Want warehouse-managed freshness?         → materialized_view / dynamic_table
Need history of changes?                  → snapshot
```

### 26.4 Cross-adapter function equivalents
| Operation | Snowflake | BigQuery | Databricks/Spark | Postgres/Redshift |
|---|---|---|---|---|
| Date diff | `datediff(day,a,b)` | `date_diff(b,a,day)` | `datediff(b,a)` | `b::date - a::date` |
| Date trunc | `date_trunc('month',x)` | `date_trunc(x, month)` | `date_trunc('month',x)` | `date_trunc('month',x)` |
| Current ts | `current_timestamp()` | `current_timestamp()` | `current_timestamp()` | `now()` |

| Semi-structured | `variant`, `:` | `json`, `json_value` | `from_json`, `:` | `jsonb`, `->>` |
→ Prefer `dbt.*` macros / `dbt_utils` for portability.

### 26.5 Run-order cheat sheet (`dbt build`)
`seeds → snapshots → models (DAG order, per node: run then its tests) → unit tests (run before their model) → exposures/metrics not executed`. A failing node **skips** its descendants (tests of upstream failing = skip downstream unless `--warn-error`/severity warn).

### 26.7 Glossary
- **DAG**: directed acyclic graph of model dependencies.
- **Grain**: what one row in a table represents.
- **Idempotent**: safe to rerun with the same result.
- **Slim CI**: build only changed nodes and descendants using state.
- **Defer**: use another environment's relation for unselected upstream nodes.
- **Contract**: enforced column names/types/constraints at build time.
- **Exposure**: downstream consumer declaration.
- **Mesh**: multi-project dbt architecture with cross-project refs.
- **Fusion**: Rust-based dbt engine with static analysis.
- **MetricFlow**: query engine behind the dbt Semantic Layer.
